# records-retrieval

Two pieces of getting a patient's medical records for a personal-injury case, each built small and measured honestly:

1. **Find the provider** ([`matching/`](matching/README.md)): where should the records request go? A provider name and address typed the messy way people type them, matched to the right NYU Langone location in the public NPI Registry, or "no confident match" instead of a guess.
2. **Process the records** ([`records/`](records/README.md)): what came back? Duplicate pages removed without losing unique content, then a medical chronology where every entry cites a page and is checked against it.

Both come from problems named in Codes Health's Software Engineer posting: *"Matching patients and facilities across messy provider networks, where a single system like NYU Langone is 340+ care locations with no clean way to match them"*, and *"Processing records that average 300 pages, sometimes hit 30,000, and run roughly 70% duplicate, and still surfacing what matters to a case."* The step between them, sending requests and chasing them until records arrive, is not built here.

## Results so far

Each folder's README has the full output, how the test sets were made, and what each part gets wrong. The numbers below are copied from what the scripts print.

**Find the provider:** 1,000 held-out queries generated by a seeded script from real registry records (`cd matching && python evaluate.py --queries generated`):
```
| method                  | correct      | accuracy | answered | right when it answered | confidently wrong |
|-------------------------|--------------|----------|----------|------------------------|-------------------|
| baseline (closest name) |  603 / 1000  |    60.3% |     1000 |                  60.3% |               397 |
| matcher v2              |  862 / 1000  |    86.2% |      813 |                  97.9% |                17 |
```
- When the matcher gives an answer it is right 97.9% of the time. Picking the closest name is right 60.3% of the time and never says it can't tell.
- v2 is v1 plus one rule: never answer with a pharmacy or supplier.
- [`matching/README.md`](matching/README.md) also has v1, and the original 163 hand-written test queries.

**Process the records, duplicate removal:** each case file is about 400 pages, two thirds of them copies. Duplicates removed, by test set (`cd records && python eval_dedup.py --split <set>`):

| test set | v1 | v2 | v2: unique pages lost | v3 | v3: unique pages lost |
|---|---|---|---|---|---|
| this repo's own generator, held out for v1 (`test2`) | 99.9% | 99.3% | 16 | 99.3% | 16 |
| independent generator #1, used to develop v2 and v3 (`alt`) | 29.5% | 76.5% | 8 | 83.0% | 9 |
| independent generator #2, **held out for v2**, then used for v3 (`alt2`) | 35.1% | **57.1%** | **0** | 62.8% | 0 |
| independent generator #3, **held out for v3**, run once (`alt3`) | 17.1% | 22.9% | 2 | **67.0%** | **4** |
| independent generator #4, **held out**, run once (`alt4`) | 67.5% | 81.7% | 1 | **86.7%** | **8** |
| independent generator #5, **held out**, run once (`alt5`) | 64.5% | 80.6% | **12** | 84.4% | 15 |

- **The honest numbers are in bold:** v2 on `alt2` and v3 on `alt3`, each frozen before its set was run. Three separate agents wrote three more generators without ever seeing the detector, so the files have their own layouts, date formats, stamps and OCR damage.
- **v3 learns each file's own stamps** from copies it is already sure of, so it handles overlay wordings it has never seen: 67.0% on `alt3` against v2's 22.9%. The cost: 4 of 1,032 unique pages lost on `alt3`, all look-alike records merged (two custodian certifications, a corrected report and its original, two chiropractic visits). On `alt4` the pattern repeats: v3 removes 86.7% against v2's 81.7% but loses 8 unique pages against v2's 1. Because a lost page is the costly error in a legal file, **v2 stays the default** and the viewer uses it.
- **The timeline checker's date reader** was then widened (apostrophe years, compact dates, "the 14th day of March", OCR-garbled date-of-service labels, fax dates ignored) and frozen before `alt4`. On `alt4`, held out, it dropped no correct entry. With 30% of answers falsified, 4 of 637 kept entries were wrong, each a date moved onto a signature date on a page whose visit label ("Arrival:", "Seen:") the checker does not know.
- **A page-level visit-date rule** then replaced label-by-label fixes: a date that nearby words name as a signature, report, print, receipt, birth or prior-study date cannot support an entry. It was frozen before `alt5` and run once. With 30% of answers falsified, 470 of the 472 entries kept were correct. Of 626 correct entries, 13 were dropped, mostly because a title like "PROGRESS REPORT 04/21/23" makes the visit date look like a report date. On `alt5`, v2 also lost 12 unique pages, mostly a corrected billing statement merged into the original. Details: [`records/README.md`](records/README.md).
- **v1 was built on this repo's own generator:** 99.9% there, but about a third on files it had never seen.
- **v2 replaces the format-specific rules with general ones:**
  - character fingerprints;
  - page stamps found by behavior;
  - dates read in any format;
  - names that must match.
- **On `alt2`, v2 removed 57.1%, lost no unique page, and never merged two different pages.** It left 43% of the duplicates in, mostly copies with overlay stamps in unfamiliar wordings; that is what v3 was built for.
- The full account, including a first test run that lost 33 pages, is in [`records/README.md`](records/README.md).

**Process the records, chronology:** Claude (Opus 5.5) on the first 11 of the 16 held-out case files (`cd records && python eval_chronology.py --extractor claude --split test2 --cases 11`):
```
events found:              351 / 352 = 99.7%
entries correct:           351 / 351 = 100.0%
citations on the right record: 829 / 830 = 99.8%
```
- The run stopped at 11 when the account's monthly API spending limit was reached; the other 5 have not been run.
- Handed answers with 30% of the entries falsified, the checker dropped all but one. The one that got through had its date moved onto another date printed on the same page.

The details are in [`records/README.md`](records/README.md).

## Try it

Python 3.10+ and Node 18+.

```
pip install -r requirements.txt
cd records && python generate.py && cd ..        # the synthetic case files (not in the repo; rebuilt exactly from seeds)
cd web && npm install && npm run build && cd ..
uvicorn api:app --port 8010
```

Then open http://localhost:8010. It starts on an **Overview**: the two steps, how they fit together, and the results exactly as the evaluation scripts printed them. Each step has a **Take the tour** button.

- **Find the provider** (tour: http://localhost:8010/#match/tour):
  - five ready-made examples, each labelled with the one behavior it shows (a typo, the pharmacy trap, registry twins, an old hospital name, a provider that isn't NYU Langone);
  - any typed lookup, or a random held-out test query scored against its label;
  - **How did it decide?** walks through that lookup in six steps with its real numbers: what was typed, how it was cleaned up, which records were compared, the score table, the decision against the thresholds, and what name-only matching would have picked.
- **Process the records** (tour: http://localhost:8010/#records/tour):
  - **How it works** walks through the chosen case file in seven steps:
    - what arrived, and from whom;
    - one copy with the fax header, stamp and Bates number struck out, and the scan errors that still count as the same word;
    - a true duplicate pair, side by side;
    - the hard case: two therapy notes with most of their wording shared but different dates, highlighted on both pages;
    - the grouping;
    - the timeline;
    - the checker, run live on falsified entries, showing which check each one failed.
  - **Chronology:** click any citation to see its page with the quote highlighted.
  - **Duplicates:** each kept page beside the copies that were removed.

Each walkthrough step states the rules that step follows. The layout follows GnoRA's admin reasoning walkthrough. Every example in a walkthrough is computed from the same functions the pipeline uses, and tests check that each example is what it claims to be.

For frontend work, run `uvicorn api:app --port 8010` in one terminal and `npm run dev` in `web/` in another, then open http://localhost:5173. API docs are at http://localhost:8010/docs.

`npm audit` reports an advisory against the Vite dev server (`npm run dev`), and the fix needs a major Vite upgrade. It does not affect the built page that FastAPI serves.

## Layout

| Path | What |
|---|---|
| `matching/` | The provider matcher, its labeled queries, evaluation, and its API (`match_api.py`) |
| `records/` | The synthetic case-file generator, duplicate detection, the chronology with checked citations, evaluations, saved results, and its API (`records_api.py`) |
| `web/` | One React + TypeScript app with a section for each part (`src/match/`, `src/records/`) |
| `api.py` | One FastAPI server that puts both parts' routes together and serves the built page |

Each part also runs alone from its own folder; neither imports the other.

## Data

- **No patient data anywhere.**
- `matching/` uses public NPI Registry organization records.
- `records/` uses invented patients, clinicians and providers, made by its generator.

The records part reuses a few pieces of GnoRA, all written by Luis Roman; `records/README.md` lists exactly which.
